三、 项目问答逐字稿 (Q&A)
1. 简单说说 LangGraph 是什么？为什么用它而不用原来的 LangChain Agent？
答：
LangGraph 是 LangChain 官方推出的一个专门用来构建状态机（Stateful）多智能体应用的框架。
以前我们用 LangChain 的 AgentExecutor，它本质上是个“黑盒”的 while 循环（比如 ReAct），让大模型自己去想下一步调什么工具。这种做法做做简单的问答还行，但一碰到复杂的业务流程就彻底失控了，很容易陷入死循环，或者中途忘掉最初的目标。
而 LangGraph 的核心思想是把流程图化（Graph）。我们把不同的 Agent 封装成图里的“节点（Nodes）”，把流转逻辑写成“边（Edges）”，数据通过一个全局的 State 在节点之间传递。
在这个项目里，调研、检索、分析、写报告是一个有着明确先后顺序的流水线。用 LangGraph，我能精确控制 Planner 必须在 Scout 之前跑，Analyst 必须评估完了才能决定是去 Reflect 补搜还是去 Write 写报告。这种“可控的灵活性”是传统的 LangChain Agent 根本做不到的。
2. 你的系统里有几个 Agent？它们是怎么配合的？
答：
整个系统里我设计了 7 个核心的角色（Agent），它们就像一个微型智库团队，分工非常明确：
Intent Router（意图分流）：是个门卫。如果用户只问“你是谁”或“今天天气”，它直接路由给 Direct Responder 秒回；如果遇到“帮我调研一下2026年AI趋势”，它就把任务丢给深度调研管线。
Planner（架构师）：接到调研任务后，它不做搜索，只负责把大问题拆解成 3-4 个具体的子问题，并输出一个 JSON 格式的检索计划。
Web Scout（网络侦察兵）：拿着子问题，去调用 Bocha API 进行全网搜索，然后过滤掉广告和无关信息。
Local Scout（本地侦察兵）：同样拿着子问题，去查我们企业本地的 Milvus 知识库，找内部规定或历史研报。
Evidence Judge（证据裁判）：这是个关键角色。它把网络和本地收集来的信息放在一起，进行交叉比对。如果发现自媒体说 A，官方网站说 B，它会打上一个冲突标记。
Analyst（分析师）：拿着裁判过滤后的干净证据，尝试回答 Planner 最初拆解的子问题。最重要的是，它要评估“现有证据够不够？”不够的话，它会输出一个 missing_gaps（信息缺口）。
Writer（主笔）：只有当 Analyst 认为证据充足了，任务才会流转到 Writer。它负责把散碎的结论，写成一篇逻辑严密、带引用角标的两三千字深度长文。
3. 你刚刚提到 Analyst 会发现信息不够，那系统怎么处理？（重点：反思与补搜机制）
答：
这是我们系统解决“大模型胡说八道”的核心设计之一，我叫它动态反思与补搜（Reflection & Re-search）。
在传统的系统里，搜索完就直接让大模型写，写不出就瞎编。我的做法是，在 Analyst 节点加了一道卡。
Analyst 的 Prompt 里有一项明确任务：对比手头的证据和最初的子问题。如果它发现比如“2026年大模型趋势”里，缺乏关于“端侧小模型”的具体数据，它就必须把 needs_more_research 这个字段设为 true，并列出缺失的信息（missing gaps）。
这时候，LangGraph 的条件边（Conditional Edge）就会捕获到这个状态，把流程不导向 Writer，而是路由到一个叫 Reflect 的节点。
Reflect 节点看到缺口后，会专门生成几个新的、更刁钻的搜索词，然后再把控制权交回给 Web Scout 和 Local Scout 去做第二轮检索。
当然，为了防止死循环，我在全局 State 里维护了一个 iteration 计数器，最多补搜 2 轮。这就大大提升了最后生成报告的深度和严谨性。
4. 这个项目里的两层记忆系统是怎么设计的？
答：
为了让 Agent 像个懂你的私人助理，我设计了短期和长期两层记忆架构。
短期记忆（Short-Term Memory）：
主要是为了保证单次对话上下文不断层。我用了 LangGraph 自带的 Checkpointer 机制，底层接了 PostgreSQL。它用 thread_id 隔离，保存最近几十轮的对话。
但这有个痛点，对话一长 Token 就爆炸。所以我加了个阈值拦截，一旦消息超过 20 条，我就触发一个专门的摘要模型（Qwen-Plus）去做滚动压缩，把旧聊天变成几百字的摘要。
长期记忆（Long-Term Memory）：
这个是为了跨会话记住用户的习惯。
我把它分成了两类：一类是语义记忆（Semantic），存的是用户的偏好，比如“我叫小李”、“写报告时用词通俗点”；另一类是情景记忆（Episodic），存的是历史做过的任务。
底层的存储是 PostgreSQL 打底，加上 Milvus 向量索引。
5. 这些记忆是怎么注入到 Agent 里的？
答：
这里我用的是会话拦截与注入机制。
当用户发来新消息时，在进入多智能体图（Graph）之前，MemoryManager 会先拦截一下。
它会把用户的 Query 拿去 Milvus 里做一次向量检索，找出跟当前问题相关的历史事实。同时，去数据库里捞出这个用户的 Profile（画像）。
然后，我把这些拿到的 Profile、相关历史记忆、以及短期对话摘要，拼成一段专门的 [跨会话记忆] 文本。
在给 Planner 或者 Intent Router 传 Prompt 的时候，我通过一个叫 with_memory_context 的包装函数，把这段记忆偷偷塞在系统提示词的最后面。
这样，大模型在规划或者回答时，潜意识里就带上了用户的偏好，比如它会自动用通俗的语言回答“小李”的问题。
6. 你提到了向量检索，你们用了什么库？检索算法是怎么做的？
答：
向量库我用的是 Milvus，因为它是分布式的，支持海量数据，而且我们用的是 langchain_milvus 的集成。
Embedding 模型接的是阿里的 DashScope（text-embedding-v1）。
在检索算法上，我做了一个降级兜底的混合策略。
首先，当需要查记忆或者查知识库时，我首选去 Milvus 里做向量的相似度搜索（Cosine Similarity），找 Top-K 的结果。
但向量检索有时候在过滤确切的租户（tenant_id）或用户（user_id）时，如果不加严谨的标量过滤，容易窜数据。所以我在 Milvus 的 metadata 过滤上做了强约束。
如果因为某些原因（比如刚才你提到的 schema source 字段缺失导致的写入失败，或者 Milvus 宕机了），检索不到或者抛异常，代码里会立刻 Catch 住，降级去查 PostgreSQL 里的文本模糊匹配（ILIKE）。
虽然字面匹配不如语义好，但保证了系统绝对不会因为向量库出点小毛病就彻底挂掉，可用性很强。
7. 遇到过写入 Milvus 报错 Insert missed field source 吗？怎么解决的？
答：
遇到过，这个坑其实挺典型的，属于 Schema 不一致导致的。
原因：
当时我们的 Milvus Collection 在早期建表的时候，把 source 这个字段设成了必填（nullable=false）。
但在后来的迭代中，业务分叉了。一个是 RAG 知识库入库，它会带上文件的 source 路径；另一个是 Memory 记忆入库，它传的 metadata 里可能只有 user_id 和 memory_type，没有 source 这个字段。
这时候用 LangChain 往里一插，Milvus 发现少字段，直接报错抛弃了这条数据，导致长期记忆一直存不进去。
怎么解决：
我从代码层做了个统一的拦截兜底。在 _index_memory_milvus 这个写入函数里，我给传进来的 metadata 做了一次清洗。如果发现没有 source 字段，我就强制给它赋一个默认值，比如 source="memory"。
另外，从架构长远来看，我还推动了把 RAG 知识库的 Collection 和 Memory 的 Collection 在物理上分开。两套表结构各自演进，彻底解耦，这就从根源上杜绝了字段冲突的问题。
8. 这个系统怎么处理口语化的、模糊的表达？
答：
这是意图识别节点（Intent Router）的一个重要职责。
用户很多时候说话是很随意的，比如“帮我查下明天的限行”或者“最近比较火的工具”。
我的做法是：
第一，在 Intent Router 的 Prompt 里注入当前的系统时间（具体到年月日星期）。
第二，除了让它分类路由，我还要求它输出一个 reason 字段，并且隐式地去把用户的模糊查询进行结构化转换。如果它判断是复杂任务，它会把带上下文的需求传给下一环的 Planner。
Planner 的 Prompt 里被严格要求：“必须把用户的自然语言，转化为针对搜索引擎的精确关键词（search_queries）”。
这样经过两次 LLM 的“翻译”，原本模糊的口语就被洗成了搜索引擎能直接使用的高质量 Query。
9. 为什么后端选了 FastAPI？怎么跟 LangGraph 结合的？
答：
选 FastAPI 是因为这个项目有大量的网络 IO 密集型操作。
LangGraph 里每个节点调大模型、调 Bocha 搜索 API、查 Milvus，全都是在等网络。FastAPI 是基于 Starlette 的异步框架，原生支持 async/await，处理这种高并发的等待特别合适。
在结合上，我没有把大模型的逻辑硬塞进路由里，而是做了一层很清晰的隔离：
我写了一个 WorkflowService 单例，在这个 Service 里初始化 build_agents 和 build_workflow_app。
当 FastAPI 的请求进来时，调用 workflow_service.run。如果是普通的 /run 接口，就 await 等整个图跑完拿到 final 结果；
更重要的是我实现了一个 /stream 接口（SSE，Server-Sent Events）。
10. 你们的前端流式进度是怎么做的？我看效果挺好。
答：
为了缓解用户等一两分钟带来的焦虑感，我在前后端做了一套真实节点状态追踪。
后端：
在 FastAPI 的 /stream 路由里，我用 asyncio.create_task 把图的执行放进后台跑。
之前尝试过写死的循环假进度，体验很差。后来我改成了基于真实调用的事件推送。我们在节点（Nodes.py）里打印日志，但对于前端，我通过返回包含 type: "status" | "phase" | "route" | "final" 的 JSON 字符串流。
当 Intent 路由结束，推一个 route 事件；当最后大模型写完，推一个 final 事件。
前端（Vue3）：
前端用 fetch 获取 ReadableStream，然后用 TextDecoder 一点点解包。
拿到事件后，如果是 phase/status，就推到左侧/顶部的进度列表里，用动态滚动的方式展示，比如“Planner 正在拆解问题...”；拿到 final 后，直接用 markdown-it-py 类似的前端库（项目中自己手写了简单的正则+替换逻辑）渲染成漂亮的 Markdown 报告。
这样用户能清清楚楚看到系统到底在查什么，体验非常像 ChatGPT 的高级数据分析模式。
11. 项目遇到过最大的难点是什么？
答：
最大的难点其实是多智能体状态（State）的膨胀与 Token 控制。
最开始开发的时候，我把所有搜索回来的网页正文（几万字），全往 State["web_search"] 里塞。结果传到 Analyst 节点的时候，经常触发大模型的 Token 上限报错，或者模型被长文本“绕晕”了，找不到重点。
怎么解决的？
我做了一个叫“渐进式摘要与信息剪枝”的策略。
在 web_search_node 节点，我不再把几千字的原始网页直接塞给状态。我让 Web Scout 拿到 Bocha 搜索的原始数据后，用代码逻辑（非 LLM）强行截断，比如只取 snippet 的前 500 个字符。
同时，规定 Web Scout 输出的数据结构必须是严格的 JSON，只保留有用的 source_id、title 和一段精简的 snippet。
到了 Evidence Judge 环节，进一步把无效或冲突的 evidence 剔除掉。
经过这两道漏斗，最终流到 Writer 节点的信息，虽然覆盖面广，但体积被压缩了 80%，完美解决了 Token 爆炸和注意力涣散的问题。
12. Vibe Coding / AI 辅助编程在这个项目里是怎么落地的？
(注：如果面试官主动问起 AI 辅助开发)
答：
这个项目有相当比例的代码是我和 AI 工具结对编程（Pair-programming）完成的。但我个人的体会是：AI 是个不知疲倦的打字员，但架构师必须是我自己。
我的开发节奏是“自顶向下，先定契约”。
比如做 LangGraph 编排的时候，我绝对不会对 AI 说“帮我写个多智能体系统”。
我会先在脑子里想好数据流向，建一个 state.py，把 ResearchState 里的字段（query, plan, evidence_pool...）严严实实定义好。
然后，我给 AI 下的指令是：“我有一个 State，里面有这几个字段。现在我要写一个 Analyst 节点，输入是 evidence_pool，输出必须是带有 missing_gaps 字段的 JSON。请帮我实现这个节点的 Prompt 和解析逻辑。”
当 AI 给出代码后，我重点 Review 它的异常处理和 JSON 解析部分（比如它经常忘写 json.loads 的 try-catch），然后我自己写个简单的测试脚本去验证。
这种“我定架构和接口，AI 填实现，我做 Code Review”的模式，让这个复杂项目的开发周期缩短了一半，而且代码质量完全在我可控范围内。
13. 这个项目的多 Agent 架构为什么选 Plan-and-Execute 而不是 ReAct？
答：
如果是简单的日常工具调用（比如查个天气、算个汇率），ReAct 的“思考-行动-观察”循环很好用。但我这个系统是用来写长篇深度研报的。
研报的特点是：任务重、步骤多、依赖外部大量长文本。如果用 ReAct：
第一，大模型要在一次循环里决定调搜索，下一次循环里看搜索结果再决定是不是要分析，上下文非常容易被污染，一长它就忘了最初要干嘛。
第二，Token 成本太高。每一次循环都要把前面的 Thought 和 Observation 塞回去重新推理。
所以我选了 Plan-and-Execute 变体（用 LangGraph 实现）。
我让 Planner 专心做规划，把大问题拆成子问题；让 Scout 专心做搜索；让 Analyst 专心做分析。这叫“关注点分离”。
只有在 Analyst 觉得证据不够时，才通过 Reflect 节点触发补搜。这种架构容错率极高，而且每个节点的 Prompt 都可以写得很短很专一，最终生成的研报质量才稳得住。
14. 并行检索（Web Scout 和 Local Scout）在工程上是怎么实现的？
答：
这正是 LangGraph 的强项。在定义图结构的时候，我没有把它们串联。
在 graph.py 里，从 Planner 出来的边，我同时连向了 web_search 和 local_rag 这两个节点。
LangGraph 在底层是基于 Python 的 asyncio 的。当状态流转到这一步时，框架会自动把这两个节点的任务放入事件循环中并行执行。
Web Scout 去调外网的 Bocha API 找最新资讯，Local Scout 同步去调本地的 Milvus 找企业历史数据。
只有当这两个节点都执行完毕，把各自的 evidence 写入到 State 后，下一步的 Evidence Judge（证据裁判）才会被唤醒。
这种真正的 IO 并行，把整个调研阶段的等待时间直接砍掉了一半。
15. Evidence Judge（证据裁判）的作用到底是什么？能举个例子吗？
答：
证据裁判是这个系统能被称为“深度研报助手”的关键。大模型最怕的就是被垃圾信息带偏。
网上的信息鱼龙混杂，本地知识库有时也有过时的数据。如果直接丢给 Analyst 去分析，肯定会出问题。
所以 Judge 的作用就是“清洗和对齐”。
举个例子：Web Scout 搜到一篇自媒体文章说“2026年XX工具已经倒闭了”，但 Local Scout 搜到的本地官方文档说“该工具在正常运营”。
Judge 拿到这两条 evidence 后，它的 Prompt 要求它进行交叉验证，并且根据信源的权威性打分。它会给官方文档打高分，给自媒体打低分，并输出一个 audit_flags（冲突标记）。
这样 Analyst 在看数据时，就不会被假新闻带偏，甚至能在最终报告的“风险提示”里把这个冲突写出来，显得极其专业。
16. 你怎么评估 RAG 和多智能体这套系统的效果？有什么具体指标吗？
答：
我是从“检索层”、“路由层”和“生成层”三个维度来做评估的。
检索层： 我主要看命中率（Hit Rate）。我们构造了大概几百条内部业务的测试 query。测试下来，如果是纯业务政策类问题，知识库的 Top-3 召回准确率在 95% 左右。
路由层： 也就是 Intent Router 准不准。我收集了一批真实用户的输入，既有“你是谁”这种闲聊，也有“深度分析XX行业”这种复杂诉求。现在的多意图识别准确率能稳定在 90% 以上。
生成层： 这个最难量化，所以我用了“事实错误率”和“人工抽检”结合。对于长文报告，我们会让业务同学盲测，看是否有幻觉或者瞎编来源。因为我做了强过滤和源溯源（Source Index），事实错误率比直接用单点模型写降低了 80% 以上。
17. 为什么选用 Bocha API 作为外网检索？和普通搜索引擎有什么区别？
答：
普通搜索引擎（比如直接爬 Google 或 Bing）返回的大多是 URL 和很短的 meta description。大模型光看那个 description 往往得不到什么实质内容，如果要点进去爬正文，耗时又太长，还容易被反爬拦截。
选 Bocha API（博查）是因为它是专门为 AI Agent 设计的。
我调它的 /v1/web-search 接口时，可以直接要求返回 summary。它不仅给我网页的标题和 URL，还会把网页的核心正文做一层提炼后返回。
这就省去了我自己去写爬虫和清洗 HTML 的麻烦。而且它对国内的时效性新闻、AI 趋势这些内容的收录非常快，刚好契合我们做“最新研报”的需求。
18. 如果用户的请求需要极高的实时性（比如股票、汇率），当前系统能处理吗？
答：
能处理。
对于这种高实时性需求，Intent Router 在理解意图后，Planner 会生成明确包含时间限定的 search_query（比如“2026年3月XX公司最新股价”）。
这时候，Web Scout 调用的 Bocha API 就可以发挥作用，因为它本身具备实时联网的能力。
不过，为了更严谨，如果未来这个需求非常高频，我其实会在 tools.py 里再加一个专门的 FinanceAgent 或接一个股票专用的 API，在 Planner 拆解时把它当成一个独立的并行节点加进去。这也就是我们这套插件化架构好扩展的地方。
19. 说说你们是怎么处理长文档 Chunking（分块）的？
答：
在 RAG 的入库阶段，处理长文档是个技术活。如果切得不好，上下文就断了。
我在 rag/core.py 里用的是 RecursiveCharacterTextSplitter。
我把 chunk_size 设为 500，chunk_overlap 设为 50。
这里有个细节：我自定义了 separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""]。
这意味着系统会优先按段落（\n\n）切；如果一段太长，就按单行（\n）切；再长就按句号（。）切。
这种基于自然语义边界的递归切分，能最大程度保证每个 Chunk 是一句完整的话，而不是把一个名词从中间生硬截断，这对后续的向量语义匹配非常关键。
20. 你们的向量库选型为什么是 Milvus？对比过 FAISS 或 Chroma 吗？
答：
前期原型开发的时候确实用过 FAISS，因为它是个本地库，跑起来轻量。
但在决定往生产级方向走的时候，我切成了 Milvus。
原因有三：
第一是持久化和分布式：FAISS 本质上是个常驻内存的索引库，一旦服务重启，如果不手动存取文件数据就没了。Milvus 是一个真正的数据库，支持高可用和分布式扩容。
第二是标量与向量混合查询：在我们的记忆系统里，找一条记忆不仅要算向量相似度，还要严格过滤 tenant_id 和 user_id。Milvus 对这种“元数据过滤 + 向量近邻”的混合搜索支持得非常好，性能很高。
第三是生态集成：langchain_milvus 现在的支持很完善，切换成本极低，代码里只需要换个 VectorStore 的初始化类就行。
21. 如果 Milvus 挂了，你们系统会直接崩溃吗？（容错机制）
答：
绝对不会。我在这块做了很重的兜底逻辑。
比如在查长期记忆的时候，search_semantic 方法里套了一层 try-catch。如果检测到 Milvus 连接超时或者抛了异常（比如之前提到的 Schema 不匹配），我会立刻捕获这个异常打一条 warning 日志。
然后，代码会自动降级（Fallback）去查 PostgreSQL 关系型数据库。
因为我在往长期记忆写数据时，是“双写”的。一份写向量库，一份把原始 JSON 和 Summary 存在 PG 的 memory_entries 表里。
所以就算 Milvus 挂了，PG 里照样能用 SQL 的 ILIKE 做文本模糊匹配，把相关的记忆捞出来。用户体验上顶多是没那么“懂他”了，但流程绝对不会断。
22. 长期记忆里的“偏好覆盖”是怎么实现的？
答：
人的偏好是会变的，比如以前喜欢住“如家”，现在改住“全季”了。如果系统只是一味地追加（Append），记忆就会打架。
所以在 MemoryManager 收到新偏好时，我没有简单粗暴地 insert。
如果是提取到了新的 Profile（偏好属性），我会调用一个 merge_user_profile 的逻辑。我会把原来的 Profile JSON 取出来，跟新的偏好做合并。
虽然目前用的是较简单的替换/追加逻辑，但未来这块可以专门加一个 Preference Agent，让大模型来判断“新输入是补充还是推翻”，然后输出一个 JSON Patch 去精准更新数据库里的画像，这就真正实现了记忆的新陈代谢。
23. 你前面提到用 Redis 缓存，具体缓存了什么数据？收益有多大？
答：
为了扛住并发，我引入了 Redis，主要缓存了两类热数据。
第一类是短期记忆的会话消息（Short-term messages）。因为用户一直在聊天，如果在多智能体流转的每一步都去 PG 里 SELECT 历史消息，IO 开销太大。所以我把正在活跃的 thread_id 对应的消息全放进 Redis 的 List 里，设了个 7 天的 TTL。
第二类是会话的摘要（Summary）。刚才提到消息太多会被压缩，压缩后的那个 summary 字符串也是放在 Redis 里。
收益非常明显：在压测的时候，原来每个 Agent 节点启动都要去扫一次数据库建上下文，现在全走内存级别的 Redis 捞，单个节点的准备时间从 100ms 降到了个位数毫秒级，整体响应顺滑很多。
24. 你们的前端代码是怎么跟后端对齐类型的？
答：
由于后端是 Python (FastAPI)，前端是 Vue3 (TypeScript)，类型不一致很容易出 Bug。
我在前端定义了严格的 TS 接口。比如 StreamEvent 这个类型：
type StreamEvent = {
type: 'status' | 'phase' | 'route' | 'final'
message?: string
final?: string
}
这个完全和后端 research_router.py 里通过 yield 返回的 JSON 结构是一一对应的。
在前端处理流式数据时，只要 JSON 解析出来，我就用 TypeScript 断言它是 StreamEvent，然后再去分发逻辑（是加到日志数组里，还是把 final 渲染成 Markdown）。这种契约式编程避免了很多因为字段拼写错误导致的页面白屏。
25. 前端的 Markdown 渲染是怎么处理复杂报告的？
答：
因为后端最终返回的是一篇两三千字的研报，里面有大量层级标题、列表，甚至代码块。
最开始想过引一个很重的 Markdown 库，但考虑到这个页面只需要轻量级展示，我就手写了一套基于正则和字符串替换的 markdownToHtml 函数。
核心逻辑是分两步走：
先保代码块：用正则把 ``` 包裹的内容提取出来，换成占位符（比如 @@CODE_BLOCK_1@@），防止后面的正则把代码里的特殊字符误伤。
逐行解析：按 \n 切分行，判断是不是 #（h1）、##（h2）、或者 -（列表）。处理完普通文本后，再把代码块的占位符替换回 <pre><code> 标签。
这种做法非常轻量，且完全满足了目前研报里加粗、链接、引用的渲染需求，首屏渲染速度极快。
26. 项目里怎么保证系统不会因为某个 Agent 出错就全盘崩溃？
答：
我做了几层隔离和兜底。
第一层是 JSON 解析容错：每个 Agent 输出的必须是 JSON。我在 _invoke_json_agent 里封装了一个 _extract_json_block，用正则把大模型可能带上的 ```json 这种废话剔除掉。如果 json.loads 还是报错，我会捕获异常，并返回一个该节点专属的 fallback 默认字典，保证流程图能往下走。
第二层是 图执行异常隔离：在 FastAPI 的 Service 层，我把 app.invoke(state) 放在了单独的任务里。如果真的发生了不可逆的代码级崩溃，外层的 try-catch 会接住，然后给前端返回一个友好的错误信息：“请求失败”，同时保证后端的 Uvicorn 进程不会挂掉。
27. 如果让你现在重新设计，你会对当前的意图识别（Intent Router）做什么优化？
答：
现在的 Intent Router 全靠大模型硬生生去判断。虽然准，但每次都要消耗 Token 和几秒钟的推理时间，太奢侈了。
如果重构，我会做一个分层路由：
第一层：规则引擎（Regex + 关键词 + 意图匹配树）。如果用户问“你是谁”，直接正则命中规则，0 毫秒直接走到 Direct Responder。
第二层：轻量级分类模型（比如微调一个很小的 BERT 或 FastText）。处理一些模糊但不复杂的分类。
第三层：才是现在的大模型。只有当一二层都拿不准，或者明确是长尾复杂需求时，才唤醒大模型去做深度的意图推理。
这样能把系统的平均响应时间和推理成本打下来一大半。
28. 对于大模型的 Token 消耗，你在工程上做了哪些控制策略？
答：
多智能体最容易犯的毛病就是 Token 无限膨胀。我主要卡了三个点：
输入端卡长度：刚才提到的短期记忆压缩，超过 20 条消息就强制 Summary，绝不把几十轮聊天全传给模型。
中间层做剪枝：Web Scout 和 Local RAG 搜出来的数据，强制截断 snippet 长度（比如限制 500 字符），而且在给 Analyst 看之前，Evidence Judge 会把没用的垃圾证据直接丢弃。
按需加载 Prompt：在 nodes.py 里调用大模型时，我不是把整个系统的所有规则都塞给它，而是针对不同节点注入不同的规则（也就是 Progressive Disclosure 的思想）。Planner 只看拆解规则，Writer 只看写作规则。
通过这三板斧，每次调用的上下文都被控制在了几千 Token 以内。
29. 这个项目的代码组织结构你是怎么考虑的？
答：
我遵循了“高内聚、低耦合”的原则。
整个代码分了两大块：
app/backend/：纯纯的 Web API 层。这里只有 FastAPI 路由（Router）、请求校验（Schemas）和串联业务的服务（Service）。它完全不关心大模型怎么跑。
app/mult_agents/：纯粹的多智能体引擎层。里面按职责切分了 graph.py（编排）、nodes.py（节点逻辑）、prompts.py（提示词仓库）、tools.py（工具箱）和 memory/（记忆库）。
这种隔离的好处是，明天如果产品经理说不要网页版了，要做个飞书机器人，我只需要重写一个 backend，多智能体引擎层一行代码都不用改。
30. 做完这个项目，你对 AI Agent 的未来有什么思考？
答：
做完这个项目，我最大的感触是：Agent 不应该是个无所不能的“神”，而应该是一个管理有序的“车间”。
之前大家总想着搞一个超级 Prompt 让大模型包揽一切，事实证明那是个死胡同。未来的 Agent 一定是走向垂直化和流水线化的。
就像我们这个项目里的 Plan-and-Execute 架构，把拆解、检索、评估、写作全部分开。
每个节点干最专一的事，用最合适的模型（比如简单的分类可以用便宜的小模型，最后的深度写作才用最贵的大模型）。
同时，配合完善的 RAG 知识库和长期记忆系统，给这个车间提供源源不断的“原料”。我认为这才是 AI Agent 在企业级生产环境中落地的正确形态。
31. 多用户并发提问时，系统是如何区分和隔离不同用户的记忆的？具体读取了哪些内容？
答：
这涉及到严格的租户和用户级数据隔离。贯穿整个记忆生命周期的核心字段是 user_id 和 thread_id。
首先，在隔离机制上：
短期记忆（PG/Redis）：SQL 查询和 Redis Key 都是基于 tenant_id + user_id + thread_id 作为联合主键或前缀的。这从物理表层面保证了硬隔离。
长期记忆（Milvus）：我们把 user_id 作为元数据（Metadata）打包进向量里。检索时，先查出 Top-K 相似的记忆块，然后在代码层严格校验 metadata.get("user_id")。如果发现查出来的记忆属于别人，会直接打上 tenant_or_user_mismatch 标签丢弃，绝对不会“串户”。
其次，在读取内容上：
每次 Agent 开始工作前，系统会调用 build_personalized_prompt_context 方法，为大模型做“战前简报”，主要捞取 5 类数据：
用户画像（Profile）：显式的偏好标签（如职业、写作风格）。
相关长期记忆（Relevant Memories）：根据当前问题去 Milvus 捞出来的 Top-8 语义相关的历史事实。
最近对话（Recent Messages）：当前 thread_id 下最近的 5-8 条未经压缩的原始对话。
会话摘要（Conversation Summary）：如果聊天很久了，早期被压缩的历史摘要。
最近任务（Recent Tasks）：用户最近执行过的 3 个 Agent 任务状态，避免重复踩坑。
这 5 类数据会被拼接成 [跨会话记忆]，直接塞到 Prompt 的上下文中，让 Agent 一开口就具备专属的上下文感知能力。
32. LangGraph 默认的 Checkpoint 存在 PostgreSQL 里会导致数据无限膨胀，你们在生产环境中是怎么解决这个问题的？
答：
这是一个非常真实的生产级坑点。LangGraph 的 Checkpointer 设计理念是“事件溯源（Event Sourcing）”和“时间旅行”，它记录了 Agent 思考的每一步中间状态。这就导致存在 PostgreSQL 里的 checkpoints 表是只增不减（Append-only）的。
如果不加干预，随着并发量增加，数据库很快就会被撑爆。我们的解决思路是“长短期解耦 + 定期清理”：
在这个系统中，Milvus 才是灵魂（长期记忆库），PostgreSQL 只是内存条（短期草稿本）。核心有价值的用户偏好和事实，早就被提取并固化到了 Milvus 里。
所以，PostgreSQL 里的数据是有保质期的。我们在生产环境的解法是：
垃圾回收任务（Cron Job）：写一个定时脚本，每天凌晨运行，清理掉 30 天前（或者更久）不再活跃的 thread_id 对应的 checkpoints 数据。
按月表分区（Partitioning）：稍微高级一点的做法是在 PG 数据库层面按月建分区表，比如 checkpoints_202603。等到了 5 月，直接把 3 月的整张表 DROP 掉。这比用 DELETE 语句一条条删要快得多，且不会产生磁盘碎片。
通过这种方式，既享受了 LangGraph 的状态管理红利，又完美规避了存储爆炸的风险。
33. 你多次提到“对话压缩（滑动窗口+摘要）”来防止 Token 爆炸，在代码层面具体是怎么实现的？
答：
为了防止长对话把大模型的上下文窗口撑爆，我们在 memory/manager.py 里实现了一套动态压缩机制。
具体在代码里，当调用 add_short_term_message 存入新消息后，会紧接着触发 _compress_pg_thread 方法。它的执行逻辑是这样的：
查历史与阈值判定：先去查当前 thread_id 下的总消息数（_get_pg_short_term_messages）。如果历史消息超过了设定的阈值。
滚动摘要（Rolling Summary）：系统会提取出最老的几条消息，连同上一轮已经生成的老摘要一起，发给一个专门用来做总结的 LLM 节点。Prompt 大致是：“结合已有摘要和这段新对话，生成一个更新版的摘要”。
数据库更新：拿到新摘要后，调用 _set_pg_short_term_summary 存入 short_term_summaries 表。
物理删除老消息：紧接着，执行一条 DELETE FROM short_term_messages 语句，把刚才被总结掉的那几条老消息从数据库里物理删除，只留下最新的几条。
最终，当 Agent 下次读取上下文时，看到的就是“一段几百字的背景摘要 + 最近的 5 条鲜活对话”。这种“滑动窗口 + 滚动摘要”的结合，既保留了长线的语境，又把 Token 消耗死死卡在了安全线以内。
34. 简历中提到“幻觉率由约 25% 降至 6%，引用准确率达到 94%”，这个指标是怎么测出来的？具体是怎么实现降幻觉的？
答：
这个指标是在我们企业内部构建的一个包含 200 条复杂行业查询的测评集上得出的，测评方式是“人工盲测 + 自动化脚本校验”。
如何降低幻觉：
大模型产生幻觉的根本原因是“无中生有”。我们在系统中通过三个环节把它按死了：
强制信息源依赖（Grounding）：Writer 节点在写报告时，Prompt 里被严格要求“必须且只能基于输入的 evidence_pool 写作”。如果不包含在证据池里的结论，宁可写“未检索到相关信息”，也绝对不许自己编。
证据交叉裁判（Evidence Judge）：这是最核心的一步。我们引入了评分机制，给官方财报打 1.0 分，自媒体打 0.5 分。如果 Judge 发现不同信源有冲突，它会直接把低分信源剔除（低质量信源占比从 45% 降至 12%），这从上游保证了喂给模型的数据就是干净的。
强制引用编号约束：要求生成的内容必须带有如 [1] 的合法来源编号。如果在最后输出解析时，发现大模型输出了一个 [9]，但实际证据池里只有 5 条证据，后处理正则校验就会直接把这个“幻觉引用”摘掉或报错重试。
35. 你提到研究完备性满意度由 62% 提升至 89%，这里的“完备性”指什么？是如何通过多轮迭代补搜解决的？
答：
“完备性”在研报场景里，指的是是否回答了规划阶段拆解出的所有子问题，没有遗漏关键拼图。传统 RAG 最容易出现的问题是：搜了一次，只搜到了表面信息，大模型就凑合着写了，导致报告很“水”。
为了解决这个痛点，我设计了迭代式研究闭环：
当系统进行到 Analyst（分析）节点时，它不仅仅是写结论，它的首要任务是对比“初始问题”和“当前证据池”。
如果发现证据不足（比如规划里要求查竞争对手的定价，但检索回来的全是产品介绍），Analyst 会输出一个明确的 missing_gaps（信息缺口）。
此时，状态机会触发路由流转到 Reflect（反思）节点。Reflect 节点会针对这个具体的 gap 生成更垂直、更刁钻的补充 Query（比如直接搜“XX竞品 2026年 报价单”），然后重新触发网络和本地检索。
这种“证据不足 → 自动补搜 → 再次分析”的递归闭环（限制最大迭代 2 次防死循环），把单次检索的局限性彻底打破了，所以完备性得到了质的飞跃。
36. 性能指标里写“双源检索平均响应时间 < 8s，端到端研报生成从小时级缩短到半小时内”，这个架构的性能瓶颈在哪？你们怎么优化的？
答：
多 Agent 系统的性能瓶颈永远在 LLM 推理的等待时间 和 外部网络 IO（比如搜索网页）。
为了把耗时打下来，我们在架构上做了几个关键优化：
真·并行 IO 执行：在 LangGraph 中，Web Scout（网络搜）和 Local Scout（本地查）并不是串行的。我利用 asyncio 让它们在同一个图层级并发执行。只要最慢的那个接口（通常是外网抓取）返回，这一步就结束了，检索耗时直接降低了 35%。
意图路由预筛选拦截：我们统计发现，真实场景下有 60% 的提问其实是简单的闲聊或已知知识查询。如果这部分也走完整的 8-Agent 深度研报链路，极其浪费资源。所以 Intent Router 采用了“规则+大模型”双模态，简单的直接秒回（响应只需 1-2 秒），把好钢（深度算力）用在刀刃上。
渐进式 Token 裁剪：由于我们做了严格的证据切片（Snippet 截断）和低质证据剔除，流转到最后 Writer 节点的 Token 负担大大减轻。Token 越短，大模型的首字响应（TTFT）和整体生成速度就越快。
通过这些工程优化，分析师以前需要花几小时用谷歌找资料、对比、码字的过程，现在喝杯咖啡的功夫（几分钟到十几分钟）系统就自动出具了一份带引用的高质量初稿。
